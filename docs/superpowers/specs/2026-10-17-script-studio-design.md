# 口播工作台（第一期：Shawn 自用）设计

日期：2026-10-17
状态：已回答审阅问题，待 Shawn 确认全文

## 为什么做

Shawn 写口播稿是集中一次写一批，但录要专门找时间，而且稿子在录之前会一直改。现在的问题：

1. 稿子多了没法按时间管理：哪周要录哪几条、什么时候要录完，没有地方看。
2. 每改一版都想知道念出来效果怎么样，又不想每次都真人重录。

所以要一个**按时间管理口播稿**的工作台：从 Fordexa 的公共选题里把稿子拉到自己名下，按自己的风格改，排上「要录完的日期」，改完用自己的声音让 AI 先念一遍试听，满意了再去 App 里真人录。

**先在网页上实测，好用了再搬进 App。** 所以第一期追求的是「能真用、能看出好不好用」，不是功能完整。

## 目标（第一期）

1. **拉稿**：在公共选题（`idea_bank` 里的单条选题）上点「拉到我这里」，把 Fordexa 原版复制到自己的口播库。
2. **改稿**：在自己的稿子里手动改，或「按我的风格生成」（用该选题的标题 + 所属文章正文 + 出处，按「我所在公司」的提示词），可反复生成多版对比、就地改提示词。
3. **日历**：每条稿子一个日期——**要录完的日期**。默认本周视图，按天列出当天要录完的稿子。
4. **试听**：用「我的声音」把当前稿子念一遍，在网页上播放。
5. **我的声音**：在后台上传自己的录音，交给 Fish Audio 训练出声音；或者直接填一个已经在 Fish 上训练好的声音 ID。

## 不做（第一期）

- 客户自己登录网页工作台、客户自己改提示词——第二期。客户以后的登录方式是：在 App 里绑定邮箱 + 设密码，然后用邮箱登录网页（App 已有这个功能）。
- 网页上的 Apple 登录——不做。客户走「App 里绑邮箱」这条路。
- 改稿时联网补调研——不做。调研只在 Fordexa 写文章时做一次（见下面的事实规则）。
- AI 试听音频用于发布——不做，**只试听**，最终一定是真人录。
- App 里的日历/试听——网页验证好用之后另立项目。

## 反目标（做出来也算失败的情况）

- **AI 改稿时编出文章里没有的事实**（规定、金额、门槛、年份）且没被标出来。用户是律师、会计、移民中介，说错规定是他们本人的执业责任。这是整个设计里最不能出的错。
- 稿子在网页上改了，App 里打开还是旧版。
- 改一个字就重新烧一次 Fish 额度。

## 核心概念：一篇文章，两份提示词

- **文章**（Fordexa 出）：选题、正文、出处都由 Fordexa 写好，是**唯一的事实来源**。写文章时就把调研和出处做完。
- **提示词 A：Fordexa 的**：把文章做成演示用口播稿（网站上公开展示的 Fordexa 版）。就是现有的 `app_settings.draft_prompt`，只有管理员能改。第一期不动它。
- **提示词 B：公司的**：每家公司一份，基于同一篇文章、选题、出处生成这家公司风格的稿子。现有的 `organizations.style_prompt` + `style_samples` 是它的雏形。第一期只有管理员能改（现有「合作公司」页已能改）；第二期公司自己能改。
- 每份提示词**自己决定**能不能写数字、写数字要不要带日期。A 现在的规则是「不写死数字」，保留；B 可以放开。

### 系统固定的事实规则（不在任何可编辑提示词里，谁也改不掉）

生成「按我的风格」的稿子时，服务端在可编辑提示词之外再拼上一段固定规则：

1. **只能使用本条选题、所属文章正文、出处列表里出现的信息。** 文章里没有的信息不许写；需要但没有的地方，在稿子里原位插入标记：
   `【这条信息文章里没有，需要联系 Fordexa 补充调研：<缺什么>】`
2. 「出处里有」= **文章正文 + 出处列表**里有。改稿时不去抓出处网页（网页会改版、会打不开、抓取慢；文章本就是按出处写的，事实已在正文里）。

生成后，服务端用**程序（不是 AI）**做一道数字核对：

- 从生成稿里抽出所有数字类片段（阿拉伯数字、金额、百分比、年份、中文数字如「三个月」「五千」）。
- 逐个在「选题标题 + 选题原稿 + 文章正文 + 出处」里查找（要做归一化：全角/半角、千分位逗号、中文数字与阿拉伯数字互换等，具体程度由实现者定，宁可多标不要漏标）。
- 找不到的，在编辑器里**标黄**提示。不阻止保存，只提示。
- 【需要补充调研】标记在编辑器里也要醒目显示（例如标红），并且这条稿子在列表/日历上带一个「待补调研」的小标。

数字核对之外，再加一道 **AI 逐句复核**（Shawn 2026-10-17 决定第一期就做）：

- 生成完成后，再调一次 DeepSeek（独立调用，固定的复核提示词，不受任何可编辑提示词影响），输入「生成稿 + 选题标题 + 原稿 + 文章正文 + 出处」，让它**逐句**判断这句话里的事实性说法能否在文章/出处里找到依据，输出找不到依据的句子（原句 + 一句说明缺什么）。
- 输出用结构化格式（如 JSON），服务端按原句在稿子里定位后**标黄**；定位不到的列在编辑器旁边。
- 和数字核对一样：**只提示、不阻止保存**。界面上要说清楚这是辅助提示，不是保证——最终由人确认。
- 复核失败（超时、格式错）不影响拿到稿子，只显示「复核没跑成，可重试」。
- 编辑器里提供「重新复核」按钮（用户手动改稿后可以再跑一次）。

「Fordexa 原版」不做核对（那份本来就是 Fordexa 写的）。用户之后手动改稿也不强制核对，但编辑器里有「重新复核」按钮，数字核对和 AI 逐句复核一起重跑。

## 功能细节

### 1. 拉稿

> 2026-10-17 改定（Shawn）：**先拉到自己的口播库，再在自己的稿子里改**。拉的时候不做二选一。

- 入口：灵感库「行业灵感」里每条有正文稿的选题卡片/详情上有「拉到我这里」，一点即拉，**内容一律先放 Fordexa 原版**，带上选题编号（`code`，如 FX-0003）。
- 拉过来后进口播库的「未排期」，同时弹一个轻提示「已拉到口播库 · 排个日期」，点了就能直接选日期，不点也行（我的判断——Shawn 没定，选了最不打断的做法）。
- 「按我的风格生成」**在自己的稿子页里**做，见下面「3. 改稿、版本与试听」。
- 文章与选题的关系：`idea_bank` 里一篇文章是一个父行（`article` 字段），下面挂若干子选题（`parent_id` 指向父行），每条子选题有自己的 `title` 和 `script`。**按单条选题拉**。生成时用这条选题的标题 + 它所属文章（自身有 `article` 就用自身，否则用父行的）的正文 + `refs`。
- 拉过来的稿子写进现有的个人稿子表 `scripts`（App 已经在读这张表，这样网页改完 App 里就是最新版）。需要记下来源选题，便于以后在稿子上显示「来自哪篇文章」、生成时找回文章。
- 同一条选题可以重复拉，不做去重（同一条稿子里本来就能生成多版，重复拉的需求很少）。

### 2. 日历

- 每条稿子一个可空日期：**要录完的日期**。
- 默认**本周视图**（周一到周日），每天下面列当天要录完的稿子：标题、状态、是否有【待补调研】、是否有试听音频。
- **过期未录**（日期已过、状态仍是待录）：标红，置顶显示（我的判断）。
- **未排期**：没日期的待录稿放在侧栏「未排期」，可以给它选日期排进去（拖拽可选，选日期必须有）。
- 能切换上一周/下一周。
- 日期随时可改。
- 状态沿用现有 `ready`（待录）/ `recorded`（已录）/ `archived`（归档）。点「已录」后从待办里淡出。
- 点一条稿子 → 打开编辑（改稿 + 试听）。

### 3. 改稿、版本与试听

- 编辑器：标题、正文、日期、状态；黄标数字和找不到依据的句子、红标【待补调研】。
- **版本**（Shawn 的使用方式：同一个选题反复生成、对比哪版好）：
  - 每条稿子有一组版本：「Fordexa 原版」（拉过来时的那份）+ 每次「按我的风格生成」产生的第 1、2、3…版。
  - **每一版记下生成它用的完整提示词**（快照），界面上显示「比上一版改了 N 处」并高亮改动。
  - 每一版各自有核对结果（黄/红标）和试听。
  - 「**用这版**」= 把这一版设为稿子正文（`scripts.body`）。App 读到的、试听念的都是正文。之后手动改正文不影响各版本留档。
  - 版本只在网页工作台里可见；App 只看正文。
- **提示词就地改**：稿子页的生成区里直接展示「这一版用的提示词」，可以就地改后点「再生成一次」。
  - 就地改的是**这一次的试用稿**，不会自动覆盖默认提示词；要点「**存为我的提示词**」才写回（第一期写回 Fordexa 这家公司的提示词 B）。
  - 「我的」里也能改提示词（入口固定、好找），两处改的是同一份。
- 「试听」按钮：用「我的声音」把**当前保存的正文**合成 mp3 并播放。
  - 正文没变（hash 相同）且已有音频 → 直接播旧的，不再调 Fish。沿用现有 `scriptHash` 思路。
  - 正文改了 → 重新合成，旧文件删掉。
  - 提供「强制重念」。
- 试听音频不需要公开分发，只给本人播放。

### 4. 我的声音

- 「我的声音」挂在**人**身上（第一期只有 Shawn）。结构上要留出第二期「公司共用一个声音」的口子：查找顺序 = 个人声音 → 所属公司声音 → 默认「女大学生」（现有 `FISH_VOICE`）。
- 两种设置方式：
  1. **上传录音训练**：上传 1–20 段自己的录音（可选附上对应文字），调用 Fish `POST https://api.fish.audio/model`（multipart：`type=tts`、`title`、`train_mode=fast`、`visibility=private`、`voices[]`，可选 `texts[]`、`enhance_audio_quality`）。`fast` 模式建完即可用，返回 `_id` 就是声音 ID，存下来。
  2. **直接填 ID**：填一个已在 Fish 网站上训练好的声音 ID。
- 能看到当前在用的是哪个声音，能「用这个声音念一句试试」。
- 合成调用沿用现有 `synthesize()`，把写死的 `reference_id: FISH_VOICE` 改成传入的声音 ID。

## App 现状（2026-10-17 读 `prompter` 代码得出）

- App 是 Flutter，登录后**直接用 Supabase 客户端读写 `scripts` 表**，不缓存（只在离线时退回本机 JSON）。网页改完，App 下次加载即最新。
- App 保存时 `upsert` 只带它认识的字段（`id/title/body/source/status/sort_order/code/user_id`），PostgREST 的 upsert 只更新带上的列，所以**新加的列不会被 App 清掉**。新列必须可空/有默认值。
- App 只认 `source` = `fordexa` / 其它都当 `self`；`status` 只认 `ready/recorded/archived`。
- App 读稿子时排除 `archived`，按 `source`、`sort_order`、`created_at` 排序——还不认识录完日期。第一期 App 不改；以后 App 要按日期排时再动。

## 约束

- 技术栈沿用现有：Next.js 15 App Router + Supabase（Auth、Postgres、Storage）+ Vercel 部署。写稿 AI 沿用 DeepSeek（`/api/admin/draft` 已有调用方式）。TTS 沿用 Fish Audio（`FISH_API_KEY` 已配）。
- 鉴权沿用现有 Bearer 方式（`requestUser` / `requireAdmin`）。第一期工作台只对管理员开放即可，但**数据按 `user_id` 归属**（不是全局），这样第二期给客户开放时只需放宽鉴权、不改数据模型。
- `profiles.is_admin` / `is_fordexa_client` / 公司归属只由服务端写，客户端不可改——保持现有原则。
- Vercel 函数请求体上限约 4.5MB：上传训练录音**不要经过 API 路由转发**，应由浏览器直传 Supabase Storage（签名上传链接），服务端再从 Storage 取文件转给 Fish。
- 现有 `src/app/admin/page.tsx` 已 1745 行，新功能放独立文件/路由，不要继续往里堆。
- 现有朗读用的 `idea-audio` 是公开桶（靠随机文件名防猜）。个人试听音频建议放私有桶 + 签名链接（我的判断，实现者可权衡）。
- 数据库结构现在不在 repo 里管理；本期的表结构改动要以 SQL 文件形式提交进 repo，便于复现。

## 审阅后补充的决定（我的判断，Shawn 可推翻）

- **`source` 取值不新增**：从灵感库拉来的稿子一律记 `fordexa`（它有 Fordexa 选题编号，App 上显示「来自 Fordexa」），之后换成自己生成的版本也不改；避免 App 遇到不认识的值出错。来源选题另用一个可空新列记录。新列都可空，App 不读也不影响。
- **网页和 App 同时改同一条稿子**：第一期只有 Shawn 一个人用，按「后保存的覆盖」处理，不做冲突检测。
- **Fordexa 公司**：实现时先查 `organizations` 里有没有 Fordexa，没有就建一条（`is_active = true`），把 Shawn 挂上去。副作用是 Shawn 变成「客户」口径、语音不限额——他本来就是管理员，可以接受。提示词 B 初始为空，空时只用全局骨架 + 固定事实规则。
- **【待补调研】标记**：不单独存列，每次从正文里扫描标记字符串得出。删掉标记，提示就自动消失。
- **私有存储桶**：新建一个私有桶，放个人试听音频和训练录音，播放时由服务端按需签发短期链接，过期就重新签。**训练录音在 Fish 建模成功后删除**（录音属于个人生物特征类数据，不长期留）。
- **声音设置先做「直接填 ID」**，再做「上传录音训练」。前者成本几乎为零，Fish 训练接口出问题时也有退路。

- **Fish 账号现状（Shawn 提供，2026-10-17）**：Plus 套餐，每月 250,000 积分（约 200 分钟），单次最多 15,000 字符，10 个私有音色槽位 + 1 个专业音色槽位。
  - 一条口播约 300 字，额度对试听足够；但「正文没变就不重念」的缓存仍然要做。
  - **10 个私有槽位是整个账号共用的**。第二期客户也用上传训练的话，槽位很快会满，到时要么升级套餐、要么让客户用自己的 Fish 账号。第一期不处理，但上传训练前要显示「已用 N / 10」。
- **待实测（实现第一步就做）**：Vercel 上的 `FISH_API_KEY` 是不是跟这个声音同一个 Fish 账号——私有音色只有本账号的 key 能调用。另外要确认 API 调用扣的是不是这份 Plus 套餐的积分（Fish 的 API 余额可能和网页套餐分开算）。用这个声音 ID 合成一句短话就能验证。
- **工作台登录**：沿用 `/admin` 的 Supabase 浏览器登录（同域，`browser-supabase.ts` 的会话可共用），不另做登录页。
- **时区**：「今天」「本周（周一到周日）」「过期」一律按 `Australia/Melbourne` 计算。
- **文章太长时**：生成和核对用的上下文按「选题标题 + 原稿 + 文章正文 + 出处」拼接；如超出模型上限，截断文章正文末尾并在界面提示「文章过长，已截断」。具体上限由实现者定。
